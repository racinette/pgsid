# T2 — postgresql: casts and arithmetic ignore operand nullability

**Status:** drafted, not filed. Against sqlc v1.31.1 (`a95e91d70`).

**Title.** postgresql: `x::t`, `a + b` and `NULLIF(a, b)` are inferred NOT NULL
regardless of operands (and `NULLIF` is also typed `bool`)

## Body

Three branches of `internal/compiler/output_columns.go` set `NotNull: true`
from the RESULT TYPE without consulting the operands:

- **`*ast.TypeCast`** (branch at line 349) builds the column with
  `toColumn(n.TypeName)` at line 361, whose `NotNull` is the placeholder
  described below. The only adjustment is a special case for the literal
  `NULL` as the argument.
- **`*ast.A_Expr`, mathematical operator** (line 157):
  `&Column{DataType: "int", NotNull: true}`, hard-coded.
- **`*ast.A_Expr`, comparison operator** (line 154):
  `&Column{DataType: "bool", NotNull: true}`.

The placeholder all three lean on is `internal/compiler/to_column.go:29`:

```go
NotNull:   true, // XXX: How do we know if this should be null?
```

unchanged since #514 (2020-05-19). The pattern is "I recognised the node, so I
know its type, so I emit a concrete column" — and a concrete column takes that
default; branches that do not recognise a node fall through to
`DataType: "any", NotNull: false`, which is correct.

`NULLIF` lands in the comparison branch because PostgreSQL's raw parse tree
renders `NULLIF(a, b)` as an `A_Expr` named `"="`. That gives it the wrong TYPE
as well as the wrong flag.

## Reproduction

```sql
CREATE TABLE foo (a int, b int);
CREATE TABLE author (id bigserial NOT NULL);
CREATE TABLE av (id bigserial PRIMARY KEY, vals text[] NOT NULL);
```

| query | sqlc IR | PostgreSQL |
|---|---|---|
| `SELECT a + b AS s FROM foo;` | `s int NOT NULL` | `a=1, b=NULL` → `NULL` |
| `SELECT a::text FROM foo;` | `a text NOT NULL` | `a=NULL` → `NULL` |
| `SELECT NULLIF(id, $1) AS r FROM author;` | `r bool NOT NULL` | `id=1, $1=1` → `NULL`, and the type is `bigint` |
| `SELECT id, v::text FROM av, unnest(vals) WITH ORDINALITY AS y (v, i);` | `v text NOT NULL` | `vals = ARRAY['a', NULL]` → `NULL` on row 2 |

The last row isolates cleanly: without the cast,
`SELECT id, v FROM av, unnest(vals) WITH ORDINALITY AS y (v, i)` correctly
reports `v` nullable. Adding `::text` flips it.

Likewise `SELECT * FROM (SELECT a AS x FROM foo) AS f` correctly reports
nullable, so subquery propagation is fine — it is the expression branches.

For contrast, sqlc gets `COALESCE` right (`COALESCE(a, 0)` NOT NULL,
`COALESCE(a, b)` nullable) and `CASE` right (conservatively nullable), so the
fix is filling in the same shape for these three.

## Expected

A cast is nullable if its argument is; an arithmetic or comparison operator is
nullable if any operand is (all the built-in ones are strict); `NULLIF(a, b)`
is ALWAYS nullable by definition and has `a`'s type.

## Cases in sqlc's own testdata that this changes

`null_if_type`, `subquery_calculated_column`, `unnest_with_ordinality`,
`func_call_cast`, `star_expansion_series`.

The first three convict the branches with no parameter involved; the last two
reach a NULL only under a NULL parameter binding that sqlc's IR declares out of
contract, and are recorded that way in their `adjudication.json`.
